## 2. Safe upgrade procedure
1. **Snapshot:** `git status` — commit or stash any new local edits first; also push `main` to a dated backup branch on `fork` (e.g. `backup/pre-upgrade-YYYYMMDD`) since `fork/main` has diverged and must not be force-clobbered.
2. **Merge upstream INTO `main`** (don't `reset --hard` / `checkout` over local edits — that silently drops them):
   `git fetch origin && git merge origin/main`  *(NB: in this repo `origin` = bytedance upstream, `fork` = your GitHub fork.)*
3. **Resolve conflicts.** Root `CLAUDE.md` may conflict (keep our playbook + re-append `@AGENTS.md`). `docker/docker-compose.yaml` will conflict whenever upstream touches the gateway volumes/env — **keep the dir-mount + writable-`extensions_config.json` split** (see §1) and the gateway's `exec` + `init: true` until #6836 lands upstream (§1 row `6a9f11cf`) while adopting upstream's other changes; `backend/tests/test_compose_extensions_config_writable.py` is adapted to this layout — restore the adaptation if upstream edits it. Do not accept "theirs" blindly; verify fork deltas did not silently drop (conflict surface on 2026-10-02: 14 files vs 2143 upstream-changed). (nginx.conf no longer diverges — upstream ships our `X-Forwarded-Proto` map since #3793.)
4. **Config schema:** if `config.example.yaml`'s `config_version` is now higher than `config.yaml`'s, copy `config.yaml` to `config.yaml.bak-v<old>-YYYYMMDD` first, then run `make config-upgrade` (merges new fields, **keeps** your `models`; it also overwrites `config.yaml.bak` with the pre-run copy and strips comments). Review the diff. 2026-10-02: v33→v50, 29 added fields, no value migrations fired.
5. **Recreate:** `make up` (rebuild + recreate) or `bash scripts/deploy.sh start` (no rebuild; recreates only changed services with the correct env/secrets). Do **not** use a bare `docker compose up` — it skips deploy.sh's `${...}` interpolation + secret loading and will misconfigure the gateway.
6. **Verify** (section 3).

## 3. Post-upgrade verification
```bash
# Gateway healthy
docker ps --filter name=deer-flow-gateway --format '{{.Status}}'
docker logs --tail 5 deer-flow-gateway          # expect: "Application startup complete"

# Default model + vision intact  → expect: minimax ollamacloud/minimax-m3 True
docker exec deer-flow-gateway sh -c 'cd /app/backend && PYTHONPATH=. uv run python -c "from deerflow.config import get_app_config as g; m=g().models[0]; print(m.name, m.model, m.supports_vision)"'

# Hot-reload hardening still active → expect a /app/deer-flow-runtime dir mount, NOT a single-file /app/backend/config.yaml
docker inspect deer-flow-gateway --format '{{range .Mounts}}{{.Destination}} {{end}}'

# view_image tool wired for the default (vision) model → expect: True
docker exec deer-flow-gateway sh -c 'cd /app/backend && PYTHONPATH=. uv run python -c "from deerflow.tools.tools import get_available_tools as t; print(\"view_image\" in [x.name for x in t(model_name=\"minimax\", include_mcp=False)])"'

# Public login works (no 403). Unauthenticated → expect 302 to pangolin …/auth/resource… (or 200 if edge-authed)
curl -sI "$(grep -m1 '^GATEWAY_CORS_ORIGINS=' .env | cut -d= -f2)" | head -1

# Forwarded-HTTPS chain honored (Secure attr present). NB semantics changed with upstream #4255
# (2026-07-27 merge): logout now CLEARS csrf_token (Max-Age=0) and suppresses re-issue — that
# clearing cookie WITH "Secure" is the expected output. Cookie *persistence* is now set at login:
# "keep me signed in" (remember_me, default ON) → access_token+csrf_token get matching Max-Age.
curl -s -i -X POST http://localhost:2026/api/v1/auth/logout -H "X-Forwarded-Proto: https" | grep -i "set-cookie:.*csrf_token"   # expect: csrf_token=""; ... Max-Age=0; ... Secure

# web_fetch provider = self-hosted Crawl4AI, end-to-end (expect markdown, not an error)
docker exec deer-flow-gateway sh -c 'cd /app/backend && PYTHONPATH=. uv run python -c "import asyncio; from deerflow.community.crawl4ai.tools import web_fetch_tool; print(asyncio.run(web_fetch_tool.ainvoke(\"https://example.com\"))[:200])"'

# extensions_config.json is a WRITABLE single-file mount (Gateway writes it: MCP/skills APIs, Settings UI;
# the atomic temp+rename hits EBUSY on the mount point and falls back to an in-place overwrite — upstream #4852).
docker exec deer-flow-gateway python -c "open('/app/backend/extensions_config.json','r+').close(); print('rw ok')"

# config.yaml hot-reload topology: an atomic host replace stays visible by inode inside the container
stat -c %i config.yaml && docker exec deer-flow-gateway stat -c %i /app/deer-flow-runtime/config.yaml   # inodes must match
```

## 4. Gotchas & fallbacks
- **Config edit not taking effect?** Only happens if the dir-mount hardening got reverted to a single-file mount. Diagnose: `docker exec deer-flow-gateway stat -c '%i' /app/deer-flow-runtime/config.yaml` (or `/app/backend/config.yaml` on the old mount) vs the host inode. Fix: re-apply the compose hardening; as a stopgap, `docker restart deer-flow-gateway` re-resolves the mount.
- **MiniMax can't see images?** Vision requires the gateway route **`ollamacloud/minimax-m3`** — the bare `minimax` alias and `ollamapro/minimax-m3` are **text-only** (silently ignore images). Ollama Cloud retires models periodically; if vision breaks, re-probe routes against the gateway with an **unguessable** test image (random digits — text-only models false-pass red/blue by guessing). Plain `langchain_openai:ChatOpenAI` is correct here (gateway returns reasoning as `reasoning_content`; do **not** switch to `PatchedChatMiniMax`).
- **Login 403 / cookies not Secure after upgrade?** The nginx `X-Forwarded-Proto` map was likely lost in the merge — re-apply it. `GATEWAY_CORS_ORIGINS` in `.env` is a partial backstop.
- **iOS home-screen PWA: "CSRF token missing" 403 after a while?** The `csrf_token` cookie became a session cookie. Originally fixed by our PR #3872; since upstream #4255 (2026-07-27 merge) persistence is decided at **login** by the "keep me signed in" checkbox (`remember_me`, **default ON**, remembered via a `deerflow_session_persistent` preference cookie; `session_cookie.py::resolve_session_cookie_policy` → `secure_persistent` on forwarded HTTPS). If the 403 returns: re-login on the device making sure "keep me signed in" is checked. Logout clearing `csrf_token` with `Max-Age=0` is normal (#4255), not the regression.
- **Gateway env interpolation errors on recreate?** You ran `docker compose up` directly instead of `scripts/deploy.sh` — the `${DEER_FLOW_*}` vars and persisted secrets come from deploy.sh; always recreate through it.
- **`web_fetch` via self-hosted Crawl4AI (0.9.2, authed since 2026-07-27).** `config.yaml` → `tools` → `web_fetch` uses `deerflow.community.crawl4ai.tools:web_fetch_tool` with `base_url: http://crawl4ai:11235` and `token: $CRAWL4AI_API_TOKEN` (crawl4ai ≥0.9 is secure-by-default: bearer auth mandatory on everything except `GET /health`; tokenless requests → 401, and a tokenless *server* would bind loopback-only and be unreachable from the gateway). The token lives in root `.env` (`CRAWL4AI_API_TOKEN`) and reaches (a) the gateway env via deploy.sh's env_file — so a fresh var needs a gateway recreate before `$`-resolution sees it — and (b) the crawl4ai container via compose interpolation. The server is the `crawl4ai` container (own lifecycle, **not** started by `deploy.sh`/`make up`): start it **from the repo root** with `docker compose --env-file .env -f docker/docker-compose.crawl4ai.yaml up -d` (`--env-file` is required; without it compose looks for `docker/.env` and the `:?` guard aborts). It attaches to `deer-flow_deer-flow` with **no host port** and a **static IP `172.24.100.5`** — the IP exists for the HOST-side consumers: the hermes skills `web/crawl4ai-web-fetch` (host curl by IP + token file `~/.hermes/secrets/crawl4ai-token`) and `research/last30days` (`scripts/lib/reddit_public.py`, `docker exec` + container env token; that skill dir symlinks to the git repo `~/last30days-skill`). **Changing the token or IP means updating those hermes files too.** Failure triage: `Error: Crawl4AI HTTP 401` → token missing/stale on the caller side; `{"error": "Internal server error", "correlation_id": ...}` → server-side crawl failure, match the id in `docker logs crawl4ai` (e.g. Reddit's IP-based anti-bot 403 — verified 2026-07-27 to hit 0.8.6 and 0.9.2 identically, i.e. Reddit-side, not an upgrade regression). Health: `docker exec crawl4ai curl -fsS http://localhost:11235/health` (auth-exempt). Jina remains a commented fallback in `config.yaml`.
- **Tool config key silently ignored?** Community providers disagree on one spelling: `crawl4ai` and `jina_ai` read `cfg["timeout"]`, but `browserless` (`web_capture`) reads `cfg["timeout_s"]`. An unrecognised key is dropped without warning and the code default applies — our `config.yaml` carried `timeout_s` for `web_fetch` until 2026-07-27 (harmless only because the ignored value equalled the 30s default). The two `docs/superpowers/` crawl4ai design docs say `timeout_s` for the config key and now carry corrections at the top. To audit any tool entry: compare its keys against what the module actually reads (`grep 'cfg.get(' backend/packages/harness/deerflow/community/<provider>/tools.py`) — note `glob`/`grep` read theirs via `_get_tool_config_int(name, "max_results", ...)`, so a naive `.get("` grep shows a false positive there.
- **Logged-in crawling (Reddit et al).** The server carries a browser session via `crawler.browser.kwargs.storage_state` → `/etc/crawl4ai-local/session-state.json`. It is **global**: every caller (DeerFlow agent included) crawls those domains logged in, so a prompt-injected fetch can read anything that session can — keep the state file narrowed with `--domain` and prefer a burner account. Full runbook + gotchas: [docker/crawl4ai/README.md](docker/crawl4ai/README.md). Three things that fail silently: forgetting `--grant-uid 999` after rotating (container is uid 999, file is 600/uid 1000), mounting the decoy `/tmp/project/deploy/docker/config.yml` instead of the live `/app/config.yml`, and an expired session (symptom = the site 403s again, no error). The provider module is upstream-tracked since 2026-07-15 (#3821/#3942 SSRF guard; crawl4ai 0.9 adds its own server-side SSRF/TLS validation on top). General rule: config edits hot-reload, but new/changed Python code needs a **gateway rebuild** (`make up`).

- **Every run fails with "1 validation error for DeerMemConfig … model_type"?** Fixed upstream since the 2026-07-27 merge (our PR #4217, upstream `5c80c07d`): `from_backend_config` drops explicit YAML `null` values. Can only reappear if the running image predates that merge — instant fix then: set `model: {}` in `config.yaml` (hot-reloads; the failed memory-manager singleton retries on the next run); durable fix: rebuild via `make up`. The `model: {}` guard is still in `config.yaml` and stays (harmless, and config-upgrade won't write `null` while the key exists).
- **Agent suddenly limited to `[read_file, review_skill_package]` ("X is not a valid tool, try one of …")?** Historical (2026-07-15 → 2026-07-27): skill `allowed-tools` used to be a **global union across all enabled skills** (#4095/#4191), so `skill-reviewer` + its eval fixtures (loaded as real skills by the recursive scan, incl. a prompt-injection fixture declaring `bash`) collapsed every chat's toolset. **#4098 landed in the 2026-07-27 merge:** `allowed-tools` now applies only to *actively activated* skills (slash-activated, or read into `skill_context`) — passive enabled skills no longer clamp the toolset. The fixtures stay `enabled: false` in `extensions_config.json` anyway until #4164 (fixture exclusion from the scan) lands, so they don't appear as activatable skills. Host bash was never exposed here (`sandbox.allow_host_bash: false`).
- **`extensions_config.json` skill enable/disable edits not taking effect?** Still true post-2026-07-27 (verified: `lead_agent/prompt.py` keeps the `(id(app_config), user_id)` cache in `get_enabled_skills_for_config`) — file edits to extensions_config are only picked up when the AppConfig object changes. After editing the file, make any content change to `config.yaml` (a comment tweak suffices — hot-reload mints a new AppConfig and the skills cache misses), toggle a skill via `PUT /api/skills/{name}` (invalidates in-worker), call the new admin-only `POST /api/skills/reload` (process-local invalidation, added upstream #4264), or restart the gateway.
- **Host-side `pytest tests/test_auth_type_system.py` fails one test?** `test_get_auth_config_missing_env_var_generates_ephemeral` reads `backend/.deer-flow/.jwt_secret`, which in this deployment is the **production secret written by the gateway container as `root:root` 600** — unreadable from the host, and the code intentionally refuses the ephemeral fallback then (#2933). Pre-existing environmental collision, not a regression (confirmed 2026-07-15); the rest of the file passes. Run auth tests inside the gateway container if a clean pass is needed.

- **Chat streams reset every ~10s — UI toasts `Error in input stream` (2026-10-02)?** Firefox's wording for a mid-body reset; runs keep completing server-side. Evidence trail: the Tower edge's Caddy logs `"aborting with incomplete response"` / `"reading: context canceled"` per attempt (a fresh TCP connection each time — the client-side path reaped it), while nginx logs 200 + the replayed burst. Ruled out (verified): server chain + app — LAN raw streams run 72s+, Firefox-over-HTTP/2 behind a Caddy proxy runs 39s+, and an app-level Playwright replay is clean. Pattern = an idle-timeout middlebox on the client's LAN path reaping quiet SSE connections. Fix applied: `stream_bridge.heartbeat_interval_seconds: 5` in `config.yaml` (was the 15s default — too sparse to beat a ~10s idle window). The bridge is built at startup, so `docker restart deer-flow-gateway`; confirm `Stream bridge initialised: redis (… heartbeat_interval_seconds=5.0 …)` and expect `: heartbeat` comments every ~5s during quiet tool/model stretches (probe with a slow `web_fetch`). If resets persist they are not idle-based — test another browser on the same client and audit its network path for proxies/security inspection. **2026-10-10 23:53Z — still recurring, and not the server chain:** thread `39e33e7a` (run `dcdf07c8`) lost all 6 stream connections (POST + 5 GET rejoins = the full recovery budget) in 5 min and the run still finished `success` (59 msgs, 00:02:42). nginx logged every one of those streams as completed `200` + bytes (no 499/5xx/upstream errors); the gateway event loop never stalled (health probes held a 5.1 s cadence across the window); 5 s heartbeats live. Only the browser→Caddy hop fails: Tower logged `aborting with incomplete response` / `reading: context canceled` for all six (`proto HTTP/2.0`, browser LAN IP), deaths mid-data at 10 s/20 s/30 s/221 s after connect, several rejoins dying exactly 10.0 s after the previous cut. Recurring since ≥2026-08-24 on Mac Firefox **and** iPhone Safari (41 aborts on Tower; deer streams only — other vhosts abort only on normal client closures), and UniFi logged no WiFi drops in the window. Suspect the client↔Caddy leg (device network stacks / h2 via Caddy / LAN): bisect with a client-side devtools capture, `network.http.http2.enabled=false`, LAN-direct `http://10.20.31.204:2026`, or a filtered `tcpdump` on Tower while reproducing.
- **UI toasts `Unable to connect to LangGraph server … Original error: NetworkError when attempting to fetch resource.`?** Same client↔edge resets as the entry above, seen through the LangGraph SDK: `AsyncCaller.onFailedAttempt` (`@langchain/langgraph-sdk/dist/utils/async_caller.cjs`) rewrites any fetch failure whose message contains `NetworkError` — Firefox's wording for a network-level fetch failure, including a request killed by reload/navigation — into an immediate `ConnectionError`, **without retrying** (`AbortError`/`Cancel`/`TimeoutError` are rethrown as-is). So a single browser↔Caddy reset on any SDK call (history, threads, runs, stream) surfaces as this "server not running" toast even though the gateway never missed a beat — verified 2026-10-10/11: Caddy's dials to `10.20.31.204:2026` never failed and nginx logged zero connection-level failures (only 200s and client-cancelled 499s). Read the context: toast right after a reload/thread navigation ⇒ probably the in-flight call cancelled by that navigation (benign); toast while sitting on a live page or mid-chat ⇒ the recurring resets above.
- **Root cause found for the stream resets (2026-10-11 ~01:00Z): Firefox on the client Mac recycles its `*.atg.one` connections every ~10.0 s.** Packet capture on Tower (filtered tcpdump to the Mac + `:2026`): every Firefox connection to `deer.atg.one`/`herdr.atg.one` lives exactly 10.0–10.1 s, ends with a client-sent h2 GOAWAY + TLS close_notify (server FIN follows within ≤1 ms; Caddy logs `aborting with incomplete response` / `reading: context canceled` — its read is canceled because Firefox hung up), and the next connection opens the same instant — a rolling cycle running continuously (13+ waves per 130 s, all evening). Chrome's connections on the same Mac never cycle, and Chrome's deer run completed after only page-load joins; `openssl s_client` from the Mac survives 30 s+, and slow h2/h1 transfers from other hosts through the same Caddy run 57 s+ clean (control). Tell-apart fingerprint: Firefox SYNs carry ECN+`[SEW]`, Chrome SYNs are plain `[S]`. So: when the deer page runs in **Firefox**, its SSE stream rides connections that Firefox recycles ≤10 s in → `Error in input stream` → SDK rejoin → dies again; the server chain (nginx 200s, gateway, bridge heartbeats) is clean throughout. Next: audit the Firefox profile — `about:config` "Show only modified preferences" (`network.http.*` timeouts, e.g. `network.http.connection-timeout` non-default) or a user.js/extension that disposes connections; workaround meanwhile = Chrome (verified), or a fresh Firefox profile.
- **Update (2026-10-11 00:49Z) — confirmed: closing the herdr tab in Firefox stopped it instantly.** Last recycled connections 00:48:54, nothing since except two isolated one-off connections a minute apart, and the final connection is *still open* minutes later (vs exactly ~10.0 s before). So the recycling engine is the **herdr/Paseo web UI page open in Firefox** (its own ~10 s reconnect loop against the herdr bridge through the Caddy edge — cf. Firefox bug 1655372, WebSocket connection loops behind an h2 proxy), and deer-flow streams only died because Firefox **coalesces same-cert origins** (`deer.atg.one` + `herdr.atg.one`: same IP, same `*.atg.one` wildcard cert) onto the connections that page kept recycling. Mitigation: don't keep the herdr/Paseo UI in the same Firefox profile as deer-flow (use Chrome/Safari for one of them), or fix the herdr page's reconnect loop. Not a pref/user.js issue after all.
- **UI toasts `Some live updates expired…` / `Unable to recover SSE history after 5 attempts`, and the gateway logs `fell behind retained history` (2026-10-13)?** The Redis stream bridge keeps only `stream_bridge.queue_maxsize` events per run (an exact `XADD MAXLEN`, default 256). Runs here publish ~2,650 events on average (50,370 XADDs over 19 runs), with bursts of 256+ events inside ~80 ms. Any SSE subscriber that stalls or reconnects therefore falls out of the window and gets a `gap` event (`stream_replay_gap`); the frontend recovers up to 5 times (`MAX_STREAM_GAP_RECOVERIES`), then gives up. Before the fix: 44 gap warnings in 72 h, across 8 of 19 runs, on iPhone Safari, Mac Firefox and Mac Chrome alike. Fix applied 2026-10-13: `queue_maxsize: 4096` in `config.yaml` (pre-edit copy `config.yaml.bak-pre-stream-buffer-20261013`). The bridge is built at startup, so the change needs a gateway restart; confirm the log line `Stream bridge initialised: redis (queue_maxsize=4096, …)`. Cost: Redis holds ≤4096 events per *active* run (keys vanish after the run; an idle Redis has 0 keys, ~1.3 MB, and no `maxmemory`), and a cursor-less rejoin replays the whole retained window. Re-check with `docker logs deer-flow-gateway 2>&1 | grep -c 'fell behind retained history'`. (A `Load failed` toast is Safari's wording for a network-level fetch failure — the same family as Firefox's `NetworkError` above, not a server error.)
- **Gateway stops were always a hard SIGKILL. Fixed on this deployment 2026-10-13 (`6a9f11cf`; upstream issue #6835, PR #6836 open).**
  - **Root cause.** The gateway's PID 1 was `sh -c "cd backend && … uv run … uvicorn …"` (the compose `command:`, identical upstream). `sh` installs no SIGTERM handler (`/proc/1/status` SigCgt `0x10002` = SIGINT + SIGCHLD only), and the kernel drops handler-less signals sent to a PID namespace's init process. So Docker's SIGTERM never reached uvicorn, even though uvicorn does catch it (its SigCgt has bit `0x4000`).
  - **Evidence before the fix.** During `docker restart -t 45`, uvicorn kept answering `/health/ready` with 200 for the whole 45 s and never logged `Shutting down`. Then Docker sent `kill 9` (exit 137). The lifespan shutdown never ran: no 30 s memory flush (`memory.shutdown_flush_timeout_seconds`), no run drain, no channel or MCP cleanup.
  - **The fix** (row in §1's tracked-files table):
    - `exec` the server, so uv replaces `sh` (`… && PYTHONPATH=. exec uv run --no-sync uvicorn …`). uv forwards SIGTERM to uvicorn.
    - `init: true` on the gateway service. Docker's init becomes PID 1; it forwards the signal and reaps orphans. Measured on upstream-built images: `exec` alone leaves zombie orphans, and `init` alone is still not graceful.
    - From upstream #6347: `stop_grace_period: 90s` and `--timeout-graceful-shutdown 10`.
  - **Verified live after the deploy (18:26Z):**
    - PID 1 is `/sbin/docker-init`, and uv (PID 7) and uvicorn both catch SIGTERM.
    - `init=true`, and the stop timeout is 90 s.
    - An idle `docker restart` took 0.4 s, sent SIGTERM only (no `kill 9`), and logged `Shutting down` → `Application shutdown complete` → `Finished server process`.
    - The recreate that applied the fix was itself still a SIGKILL, because the old container still had `sh` as PID 1.
  - **From now on:** a restart still interrupts an active run, so keep restarting only when no run is active (no Redis keys, no `pending`/`running` rows in `runs`). If a stop ever takes the full 90 s again, a merge has probably dropped the fix: check `docker exec deer-flow-gateway cat /proc/1/cmdline` (expect `docker-init`, and `exec` in the command) and `docker inspect deer-flow-gateway --format '{{.HostConfig.Init}}'`.

- **Host `make test` reds that are NOT merge damage (upstream tip `d62d9e78`, 2026-10-02):** `tests/test_auth_type_system.py::test_get_auth_config_missing_env_var_generates_ephemeral` (the root-owned `.jwt_secret` collision above — the test clears `os.environ` by design, so it always resolves the production base dir) and `tests/test_client_langfuse_metadata.py::test_stream_abandoned_generator_cleanup_stays_inside_trace_binding` (upstream bug at the tip; reproduced on a pristine tip checkout; flaky, passed in both 2026-10-13 runs). Also, depending on test order, `tests/test_stream_bridge.py::test_make_stream_bridge_defaults[asyncio]` (first seen 2026-10-13 at `6a9f11cf`): an earlier test loads the live `config.yaml` into the process-global config, so this test builds the deployment's `redis` bridge (`queue_maxsize=4096`) instead of the default one. It passes alone and with its own file. Everything else: run the suite with `DEER_FLOW_HOME=$(mktemp -d)` — the root-owned `backend/.deer-flow` otherwise fails ~33 tests on this host.
